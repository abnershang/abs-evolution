# Implementation stages and acceptance boundaries

The goal is continuous, evidence-constrained optimization of skills, durable
experience, helper tools, task organization and optimizer strategies. Successful
tasks can supply quality, efficiency, method and reuse opportunities. Failure
is one signal, not a required starting point. A kind label or an extensible
interface is not evidence that all those behaviors have been implemented.

## Local executable path

The first delivery covers explicit receipts, typed optimization opportunities,
immutable snapshots, candidate proposals, isolated Python execution, training
feedback, protected acceptance, local promotion/rollback and pinned task leases.
It must prove denied filesystem/network access, bounded process execution,
foreground admission priority, concurrent-state safety and version stability.

The shipped synthetic case measures a narrow tool behavior. It does not measure
the quality of the whole ABS instruction set or establish downstream business
acceptance. Real model calls and offline proposal fixtures are reported
separately in verification results.

Current execution is supervised only. Seatbelt provides access isolation, not
hard RAM or aggregate scratch-storage quotas. The default backend blocks without
the reviewed-code shared-resource exception. The explicitly selected Linux
Docker backend supplies runtime-verified quotas and is exercised by a disposable
CI lifecycle: evaluation, promotion, actual pinned-version consumption, rollback
and rejection of a memory-exhausting candidate. It does not start a local Docker
daemon, enable background runs, install ABS or prove real instruction quality.
Do not treat this synthetic closed loop as desktop adoption or autonomous
model-generated improvement.

The OpenRouter adapter adds tool-free, structured model proposals with explicit
model selection, existing process credentials, restrictive routing, bounded
transport and locally validated edits. Its proposal-only command does not run
the resulting code. Live verification is separate from offline transport tests.
The Codex CLI adapter remains blocked because its zero-tool boundary cannot be
verified. OpenRouter-generated code cannot bypass the resource-isolation gate.

The hybrid provider adds a typed JEV decision before optional generation. It
chooses among explicitly supplied, baseline-bound proposals, new-content
generation and insufficient evidence. Program-owned thresholds and one shared
deadline control the branches. Judge and generator observations stay separate.
This implements candidate routing, not autonomous candidate retrieval, learned
thresholds, failure diagnosis or proof that JEV improves real task outcomes.
It preserves the hard-resource gate and changes no desktop integration.

Semantic opportunity classification now has an explicit `classify` command
backed by JEV. It judges a reviewed observation and evidence summaries, including
successful work, and returns a primary comparison dimension or a reason to defer.
It neither collects task history nor writes inferred labels into receipts.
The existing hybrid JEV route now uses objective-driven criteria instead of
requiring observed failures. Deterministic counts, permissions and promotion
checks remain code-owned. Offline adapter/route tests establish these control
paths, not JEV's accuracy on real optimization opportunities.

The separate experimental `assess` command splits presence from direction:
one three-way Choice and four non-exclusive Nouls share a bounded API request.
It preserves uncertainty and contradictory signals, records batch usage once,
and leaves legacy classification/routing defaults unchanged. The rubric and
request fingerprints distinguish experiments. This is question-design
instrumentation, not calibrated accuracy or a measured optimization benefit.

## Next outcome: one task-family comparison

Select a frequent task family and define a repeatable benchmark from approved,
de-identified cases, including tasks the current version already completes well.
Before generating candidates, fix the quality rubric, measured resource budget,
minimum useful gain and non-negotiable safety and authorization constraints.
The desired result is either better quality within the same budget or lower
measured resource use with no quality regression. A known defect is optional.

Compare the current version and one selected candidate under the same conditions.
Use training cases for iteration and fresh sealed cases for final acceptance.
Record quality and observed cost/time separately; missing measurements stay
unknown. Do not combine them into an arbitrary score or accept the generator's
self-assessment as evidence. An inconclusive or unchanged result retains the
current version. Positive benchmark results still need separately authorized,
opt-in task adoption and continued observation before a business-benefit claim.

The current exact-JSON evaluator and promotion gate measure correctness gains.
Receipt dimensions do not add cost or latency scoring. A trusted evaluator and
promotion contract for the selected objective must precede an efficiency-based
promotion; lowering `min_improvement` is not a substitute.

## Instruction and workflow evaluation

Next, add a tool-restricted task-solving evaluator for selected ABS scenario
contracts. Keep routing, authorized actions and actual task acceptance separate.
Use new sealed cases, model/runtime fingerprints and multiple task families.
Do not execute the business operations embedded in those scenario prompts.
Existing ABS offline contract checks do not by themselves measure improved
instruction behavior.

## Batch experience and candidate search

Add evidence-linked batch synthesis, conflict/expiry handling and retrieval of
useful alternatives for the explicit training-only candidate pool. Preserve provenance and
cost/error uncertainty. Use holdout acceptance only after training selection;
do not expose final answers to the optimizer. Curriculum generation should
produce sandbox tasks, never choose arbitrary live business actions.

## Meta-level evolution

Treat candidate optimizer strategies and collaboration layouts as versioned
inputs to a separate benchmark. The operator's authority, protected evaluator,
permission limits and acceptance policy remain outside candidate edit scope.
A new strategy must demonstrate gains across independent experiments, not just
improve the score used to design that same strategy.

## Desktop adoption and rollout

Before any foreground integration, establish a supported task lifecycle adapter
that pins all skill/reference/helper reads, queues optional receipts without
blocking, and accurately releases leases. Until then desktop tasks are not
protected by this registry's task protocol and no background learner is enabled.

Candidate/stable distribution, user-visible activation and rollback require a
separate release integration. An ABS Git merge, marketplace refresh, plugin
installation and running conversation adopting a version are distinct states.
Do not modify the existing updater or restart chats as part of local testing.

The initial implementation does not commit or publish code, install into ABS,
start a daemon, create an automation, change a tracked marketplace ref, send
business data to a model or transfer execution to another host. An authorized
live model smoke uses only the bundled synthetic example and its training data.
